Problem Statement & Motivation

Addressing Structural Deficiencies in Academic Library Portals

Context

⚠️ Key Operational Challenges

  • Discovery Bottlenecks: With 10,000+ catalog titles, students face choice paralysis and cannot easily locate personalized or niche reading materials.
  • Race Conditions in Reservations: High-demand physical books frequently experience collision errors and double-booking during peak checkout periods.
  • Passive Reading Habits: Traditional portals offer zero engagement or page-progress tracking, leading to high abandonment rates.
  • Microservice Over-Engineering: Network latency and token validation overhead slow down inter-module communication in simple academic setups.

💡 The DLBS Solution

  • Modular Monolith: Unified Python deployment with in-process module boundaries, ensuring rapid development and sub-millisecond data exchanges.
  • Intelligent Multi-Stage Recommender: Combines genre-affinity TF-IDF vectors with popularity consensus to eliminate cold-start issues.
  • ACID Reservation Safety: Strict state transition engine and database transactions prevent simultaneous booking collisions.
  • Integrated Feedback Loop: Reading progress directly updates the student's TF-IDF profile, creating continuous personalized discovery.
Speaker Notes: In university libraries, static search and race conditions on high-demand books cause friction. DLBS was designed to solve this with a modular in-process architecture, rock-solid concurrency safety, and real-time machine learning recommendations.

System Architecture & Component Design

Lab 3 Modular Monolith Architecture & Data Flow

Architecture

🏗️ Structural Overview

[ Web Client / Browser ] (HTML5, Vanilla JS, CSS3)
         │ HTTP / REST (JWT Bearer Auth)
         ▼
[ FastAPI Application Router Layer (src/main.py) ]
  ├── /api/catalog          (Catalog Router)
  ├── /api/auth & /users    (Users Router)
  ├── /api/reading          (Reading Router)
  ├── /api/bookings         (Bookings Router)
  └── /api/recommendations  (Recommendations Router)
         │
         ▼ In-Process Direct Function Calls (Microsecond)
  ┌──────────────┬──────────────┬──────────────┐
  ▼              ▼              ▼              ▼
[ Catalog ]   [ Users ]   [ Bookings ]  [ Recommender ]
  (M2)          (M3)          (M4)           (M1)
  └──────────────┴──────────────┴──────────────┘
         │ SQLAlchemy 2.0 ORM (Shared PK book_id)
         ▼
[ Relational Database (SQLite in-memory / PostgreSQL) ]

📐 Key Architectural Decisions

  • In-Process Modular Monolith: Avoided network hop overhead and serialization latency. Recommender reads user history directly via reading.get_history(user_id).
  • Common Abstract Interface (NFR-R2): Recommender abstract base class isolates algorithms from service and presentation layers.
  • Shared Database Primary Keys: book_id is maintained consistently across Catalog, Reading, and Bookings tables.
  • Layered Caching: In-memory TTL caching isolates expensive ML computations from frequent UI pollings.
Speaker Notes: As Architecture Owner, I designed our component structure. By choosing a modular monolith with in-process function calls, we eliminated the latency and fragility of inter-service network calls while maintaining clear module boundaries.

Module 1: Recommendation Engine

Lead: Mohammed Sinan M T (Member 1)

Module 1

1. Popularity Baseline

FR-R3, FR-R4: Aggregates reader engagement across all books.

  • Cold-start fallback for new users with zero reading records.
  • Excludes already finished books and soft-deleted catalog items.

2. Content-Based TF-IDF

FR-R2: Metadata text vectorization via scikit-learn.

  • Builds user profile by weighting vectors by reading progress (100% finished, % for in-progress).
  • Cosine similarity ranking preserves genre affinity (≥3 of top 5 share genre).

3. Hybrid & Explanations

FR-R5: Linear score combination.

  • $\text{Score} = 0.7 \times \text{Content} + 0.3 \times \text{Pop}$.
  • ensure_reason() safety net guarantees non-empty explanations on every card.

⚡ Integration, Caching & Admin Refresh (DLBS-14, FR-R6, NFR-R1)

Implemented RecommendationCache with 5-minute TTL. Added POST /api/recommendations/refresh (Admin-only) which rebuilds TF-IDF matrices from catalog and clears cached responses. Uncached request latency: ~140ms; cached latency: < 0.05ms.

Speaker Notes: In Module 1, I implemented the Recommendation Engine. We provide full cold-start support via Popularity, personalized discovery via TF-IDF cosine similarity, and an explanation on every item. In DLBS-14, I added in-memory response caching and an admin refresh endpoint.

Module 4: Booking & Borrowing

Lead: Marreddy Rushieswar Reddy (Member 4)

Module 4

🔄 Booking Lifecycle & State Rules

  • Finite State Machine (DLBS-45): 
    [ Available ] ──► [ Reserved ] ──► [ Borrowed ] ──► [ Returned ]
                       │
                       └──► [ Cancelled / Expired ]
  • Strict Validation: Illegal transitions (e.g. returning an unborrowed book) rejected with HTTP 409 Conflict.
  • Active Loan Cap (FR-B8, DLBS-50): Maximum 5 active bookings per member enforced; 6th attempt rejected with 409.
  • Automated Stock Adjustments (FR-B5): Reserving decrements available copies; returning or cancelling increments copies back.

  • Seeding Engine (DLBS-47): Authored scripts/seed.py mapping shared primary keys across 10,000 books.

Temporal holdout split partitioning user reading histories into 75% training records and 25% held-out test ground truth across 14,797 records. Tested on 34 qualifying evaluation users.

Key Empirical Finding 1: Genre Affinity (FR-R2)

Verified that when a user reads books of a given genre, at least 3 of their top 5 recommendations share that genre, proving personalization accuracy.

Key Empirical Finding 2: Response Latency (NFR-R1)

Uncached requests average ~140ms (well below 2.0s limit). Response caching provides sub-millisecond retrieval (< 0.05ms) for repeated queries.

Lessons Learned & Conclusion

Key Engineering Takeaways & Final Summary

Conclusion

💡 Key Technical Takeaways

  • In-Process Monoliths for Academic Speed: Eliminating microservice networking allowed rapid iteration while maintaining strict modular boundaries.
  • Precomputation is Essential for ML Latency: Caching TF-IDF matrices in fit() reduced response times from 1.5s down to 140ms.
  • Concurrency Must Be Solved at Database Layer: SQLite BEGIN IMMEDIATE combined with row checks reliably prevented race conditions.
  • Defense in Depth: Centralizing contracts like ensure_reason() prevents frontend visual bugs even if backend algorithms change.
